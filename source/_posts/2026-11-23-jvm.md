JVM 全称为 Java Virtual Machine，本质上是一台运行字节码的虚拟机，但它屏蔽了底层操作系统差异，使"一次编写、到处运行"成为可能。

理解 JVM 可以沿三条主线展开：
- 字节码如何被加载
- 运行时内存如何组织
- 字节码如何被执行

---

## 一、整体架构

上边的概念有点抽象，为了方便理解，可以把 JVM 想象成一家**工厂**：

- **进货部门**（类加载子系统）把原料（`.class` 文件）搬进厂房，并检查原料是否合格；
- **仓库**（运行时数据区）存放原料、半成品和加工记录，有的区域所有人共用，有的区域每个工人各一份；
- **生产线**（执行引擎）把原料真正加工成产品，其中的"熟练工"（JIT 编译器）会把常做的活提前准备好以提速；
- **保洁阿姨**（GC）自动清理没用的半成品，腾出仓库空间；
- **对外联络处**（本地方法接口）负责调用工厂外部的系统能力，比如读写文件、访问网络。

| 字节码（Bytecode） | Java 源代码编译后生成的"中间语言"，不是给 CPU 直接看的，而是给 JVM 看的。类似"世界语"，由 JVM 再翻译成各台机器能懂的语言。 |
| .class 文件 | 存放字节码的文件。你写一个 Java 类，编译后就得到一个对应的 `.class` 文件。 |
| 类加载子系统 | JVM 的"进货部门"，负责把 `.class` 文件搬进内存，并检查它是否合法。 |
| 运行时数据区 | JVM 的"内存仓库"，程序运行期间所有数据都放在这里。 |
| 线程（Thread） | 程序里的一条执行流水线。一个程序可以同时开多条流水线并行干活。 |
| 线程共享 | 所有流水线共用同一份的区域，只有一份数据。 |
| 线程私有 | 每条流水线各自拥有一份、互不影响的区域。 |
| 堆（Heap） | 用 `new` 创建的对象都住在这里。它是内存仓库里最大的房间，也是保洁阿姨（GC）重点打扫的地方。 |
| 方法区 / 元空间 | 存放类的"图纸信息"（类名、方法、常量等）的地方。JDK 8 以前叫方法区，之后改叫元空间，并挪到了堆外的系统内存中。 |
| 虚拟机栈 | 每条线程自己的"记事本"。每调用一个方法就压入一页，方法结束就撕掉一页。 |
| 本地方法栈 | 和虚拟机栈类似，但专门服务于用 C/C++ 写的 `native` 方法。 |
| 程序计数器 | 记录"当前执行到哪一行"的"书签"。它非常小，是唯一不会内存溢出的区域。 |
| 执行引擎 | JVM 的"CPU"，负责真正执行字节码。 |
| 解释器（Interpreter） | 把字节码一条一条翻译一条执行，像"同声传译"：启动快，但反复翻译所以慢。 |
| JIT 编译器 | 即时编译器。把经常执行的"热点代码"一次性编译成机器码并缓存，像"提前录好的字幕"：第一次费劲，之后飞快。 |
| GC | Garbage Collection，垃圾回收。JVM 的"保洁阿姨"，自动清掉没人用的对象，腾出内存。 |
| 本地方法接口 / 本地方法库 | JVM 调用操作系统底层 C/C++ 能力的桥梁，比如读写文件、操作网络。 |

## 二、类加载机制

一个写好的 `.class` 文件要真正能用，得先经过"安检入境"的五道关卡：**加载**（把文件搬进来）→ **验证**（检查有没有捣乱）→ **准备**（给静态变量先占好位置、设默认值）→ **解析**（把"张三家"这样的代号换成真实门牌号）→ **初始化**（真正赋上程序员写的值）。

搬家的活由"类加载器"完成。JVM 用的是**双亲委派**制度：来了活先让上级 loader 试，上级干不了才自己上手。

就像公司里问题先上报领导，领导处理不了再由你解决。

这样做最大的好处是——**核心类库不会被篡改**：就算你自己写了个假冒的 `java.lang.String`，也永远轮不到它出场，因为领导（启动加载器）会优先加载官方版本。

## 三、运行时数据区：线程私有部分

程序运行时的内存，有些是**所有线程共用**的（堆、方法区），有些是**每个线程各带一份**的。这里主要讲的是后者，可以理解为每个工人随身带的三件工具：

- **程序计数器**是一枚书签，记录"我这个工人干到哪一步了"；
- **虚拟机栈**是一个记事本，每做一件事（调用一个方法）就记一页，做完撕掉；
- **本地方法栈**是另一本专门的记事本，专门记录调用 C/C++ 底层方法的情况。

| 名词 | 大白话解释 |
| --- | --- |
| 程序计数器（PC Register） | 记录当前线程执行到字节码第几行的"书签"。线程切换回来后靠它知道从哪继续。 |
| OOM | Out Of Memory，内存溢出。内存不够用了，程序会崩溃。 |
| 虚拟机栈（JVM Stack） | 每个线程自己的"记事本"，随线程创建，随线程销毁。 |
| 栈帧（Stack Frame） | 记事本里的一页，对应一次方法调用。方法开始压入，结束弹出。 |
| 局部变量表 | 栈帧里存放方法参数和局部变量的地方。 |
| 操作数栈 | 栈帧里的"临时计算区"，做计算时先把数放这里再处理。 |
| 动态链接 | 把代码里的符号引用在运行期转成真实地址。 |
| 方法出口 | 记录"这个方法执行完后该回到哪里继续执行"。 |
| StackOverflowError | 栈满了溢出。最常见原因是方法无限递归调用自己。 |
| native 方法 | 用 C/C++ 写的方法，Java 通过它调用操作系统底层能力。 |
| 本地方法栈 | 专门给 `native` 方法用的记事本。 |
| 方法区 | 存放类元数据、常量池、静态变量的地方。JDK 8 后改名元空间。 |
| 元空间（Metaspace） | 方法区的新实现，放在堆外的系统内存里，一般只受物理内存限制。 |
| 类元数据 | 类的"描述信息"：类名、有哪些字段和方法、继承自谁等。 |
| 常量池 | 存放常量（字符串、数字字面量等）的一张表。 |
| 静态变量 | 用 `static` 修饰的变量，属于类本身，所有对象共享同一份。 |

## 四、堆分代结构与垃圾回收

堆是存放对象的大仓库。

人们观察到一个现象：**大多数对象"朝生暮死"**——刚创建出来没多久就没用了，只有少数对象能长期存活。

据此把仓库分成两间：

- **新生代**：新对象先住这，很快会被打扫（Minor GC）。里面又细分 Eden 和两个 Survivor 区，对象在里面几次倒腾还活着，就"晋升"到老年代；
- **老年代**：长期存活的对象住这，打扫得少（Major GC），一次打扫也更慢。

垃圾回收的思路是：先从"肯定还活着"的起点（GC Roots，比如栈里的变量）出发，顺着引用一条条找，能找到的对象就保留；找不到的就是垃圾，回收掉。

### 垃圾回收的核心逻辑

1. **对象存活判定**：主流采用**可达性分析**，从 GC Roots（栈中引用、静态字段、常量引用等）出发遍历引用链，不可达的对象判定为可回收。这解决了引用计数的循环引用问题。
2. **回收算法**：标记-清除（有内存碎片）、标记-整理（适合老年代）、复制算法（适合新生代，无碎片但牺牲空间）。
3. **收集器演进**：Serial → Parallel → CMS（低停顿）→ G1（区域化、可预测停顿）→ ZGC（亚毫秒级停顿，着色指针 + 读屏障）。


| 名词 | 大白话解释 |
| --- | --- |
| 分代模型 | 按对象"年龄"分区管理。因为大多数对象活不久，分开管理效率更高。 |
| 弱分代假说 | 一个经验规律："大部分对象朝生暮死"，分代设计就是基于它。 |
| 新生代 | 新创建的对象先住的区域，垃圾多，打扫频繁。 |
| 老年代 | 活得久的对象搬过去的区域，垃圾少，打扫不频繁。 |
| Minor GC | 只清理新生代的垃圾回收，速度快、次数多。 |
| Major GC | 清理老年代的垃圾回收，速度慢、次数少。 |
| Eden（伊甸园） | 对象刚出生时住的地方。满了就触发一次 Minor GC。 |
| Survivor S0 / S1 | 两个"幸存者区"。Eden 清理后还活着的对象搬进来，两个区来回倒腾。 |
| 晋升（Promotion） | 对象在 Survivor 区熬过若干次 GC 后，被搬到老年代。 |
| 元空间（Metaspace） | 存类元数据的地方，位于堆外，一般只受物理内存限制。 |

## 五、执行引擎：字节码如何真正跑起来

字节码只是"中间语言"，CPU 看不懂，必须翻译成机器码。

执行引擎有两招：

- **解释执行**：像同声传译，来一条翻译一条。好处是立刻能开工、启动快；坏处是同一句话每次都要重新翻译，慢。
- **即时编译（JIT）**：像提前录字幕，把那些反复出现的"热点代码"（频繁调用的方法、循环）一次性编译成机器码存起来，下次直接用。好处是快；坏处是第一次编译要花时间。

现代 JVM 把两招结合起来，叫**分层编译**：先解释执行让程序快速启动，再对热点代码逐级优化（C1 简单优化 → C2 深度优化），兼顾"启动快"和"跑得快"。这正是"Java 慢"的旧印象如今不再成立的根本原因。

## 总结

`.class` 文件经双亲委派的类加载器载入 → 类元数据进方法区、对象进堆、执行上下文进栈 → 执行引擎解释或 JIT 编译字节码 → GC 自动回收不可达对象 → 通过本地方法接口调用操作系统能力。

这是 JVM 的完整闭环。
