对 IO 的浅薄解读

IO 全称 Input/Output，即输入输出。

  • Input（输入，读）：外部设备（磁盘、网卡、控制台）→ JVM 程序
  • Output（输出，写）：JVM 程序 → 外部设备

Java IO 分为两大体系：

  1. java.io：传统IO，也叫 BIO（同步阻塞IO）
  2. java.nio：新IO，Java1.4 引入；Java7 升级 NIO.2，包含 NIO（同步非阻塞）、AIO（异步非阻塞）

💡BIO、NIO、AIO 分别是什么？核心区别是什么？
后文会有对照表集中解答。

一、传统BIO：字节流与字符流

java.io 下的流分为两大派系：字节流、字符流。
核心区分一句话：字节流处理原始二进制；字符流 = 字节流 + 编码转换，仅用于文本。

分类 顶层抽象父类 数据单元 适用场景
字节流 InputStream / OutputStream byte 任意文件：图片、视频、音频、文档
字符流 Reader / Writer char 纯文本文件，自带编解码

1.1 字节流家族

InputStream 是字节输入流（读），OutputStream 是字节输出流（写）。
分为节点流和处理流（装饰流）：

  • 节点流：直接对接数据源，如 FileInputStream、FileOutputStream
  • 处理流：包装其他流，增强能力，不直接对接数据源，如 BufferedInputStream、DataInputStream、ObjectInputStream

💡节点流和处理流的区别？
节点流直接绑定数据源（文件、数组）；
处理流采用包装方式，给原有流附加缓冲、序列化、类型读写等增强功能。

1.2 字符流家族

字符流底层依旧是字节，只是封装了编码解码器。
核心桥梁类：InputStreamReader、OutputStreamWriter，负责字节与字符的互相转换。

⚠️ 开发大坑：FileReader / FileWriter 底层默认使用平台编码，Windows GBK、Linux/Mac UTF-8，极易出现跨环境乱码！
生产规范：禁止直接使用 FileReader / FileWriter，优先手动指定编码！

✅ 标准写法示例

💡BufferedReader#readLine() 是否会阻塞？
会阻塞，读到换行符、回车符或者流末尾才会返回，没有数据时线程卡住等待。

常用字符流：

  • BufferedReader / BufferedWriter：缓冲字符流，readLine()、newLine()
  • PrintWriter：打印流，自动刷新，日常日志、接口返回输出很常用

1.3 IO 的核心设计模式：装饰器模式

Java IO 体系是装饰器模式经典案例。

  • 装饰器：实现同一个抽象父类，透明包装原有对象，动态增强功能
  • 适配器模式：转换接口，InputStreamReader 将字节流（InputStream）适配为字符流（Reader）

💡IO 使用了什么设计模式？装饰器模式和适配器模式的区别？

  1. Buffered 系列缓冲流是装饰器；InputStreamReader 是适配器。
  2. 装饰器：同接口，增强原有能力；适配器：转换两套不同接口，做兼容。

1.4 缓冲流原理

BufferedInputStream / BufferedOutputStream 内部维护默认大小为 8192 的缓冲区数组。

  • 无缓冲：每次 read() 都发起一次系统调用，磁盘IO，开销大，速度慢
  • 带缓冲：一次性读取一大块数据放入内存缓冲区；应用程序优先从内存缓冲区读写，大幅减少系统调用次数

💡缓冲输出流什么时候数据落盘？flush 和 close 的区别？
缓冲区满会自动刷盘；未满时需要手动 flush()。

  • flush()：把缓冲区数据刷写到目标，流还可以继续读写
  • close()：先执行 flush，再关闭流、释放操作系统文件句柄，流不能再使用

1.5 资源关闭与 try-with-resources

所有流都实现 AutoCloseable 接口，Java7 提供 try-with-resources 语法，自动关闭资源，无需手动在 finally 调用 close。
关闭顺序遵循：先创建、后关闭。

💡流不关闭会有什么后果？
流持有操作系统文件描述符（句柄），操作系统句柄数量有限，不关闭会造成句柄泄漏，最终抛出 Too many open files 异常。

1.6 对象序列化 ObjectOutputStream

序列化：对象 ↔ 字节数组，用于本地持久化、网络传输。
要求：类必须实现标记接口 Serializable（无任何抽象方法）

核心考点：

  1. transient：被修饰字段不会参与序列化，适合密码等敏感字段
  2. static 静态变量属于类，不属于实例对象，不会序列化
  3. serialVersionUID 序列化版本号

💡 1. Serializable 接口里面有哪些方法？
空标记接口，没有任何方法，仅做标记。
2. 不手动定义 serialVersionUID 会怎样？
JDK 根据类结构自动生成；类新增/删除字段后版本号变化，反序列化直接抛 InvalidClassException。生产环境必须手动指定版本号。
3. 反序列化的时候，会不会调用类的构造方法？
不会，JDK 直接从字节流重建对象实例。

二、NIO（java.nio，同步非阻塞IO）

BIO 痛点：一个连接对应一个线程，高并发场景下线程数量爆炸，CPU、内存开销巨大。
Java1.4 推出 NIO，核心三大组件：Channel、Buffer、Selector（多路复用器）

💡NIO 和 BIO 的核心差异？
BIO 同步阻塞，一连接一线程；NIO 同步非阻塞，依靠 Selector 单线程监听大量通道事件。

2.1 Channel 通道

Channel 类似流，但是有明显区别：

  1. 流是单向（输入流只读、输出流只写）；Channel 双向可读可写
  2. Channel 必须配合 Buffer 使用，数据都先读写到缓冲区
  3. 常见实现：SocketChannel、ServerSocketChannel、DatagramChannel、FileChannel

💡FileChannel 可以注册到 Selector 实现非阻塞吗？
不可以。FileChannel 是阻塞通道，只有网络相关的 Channel 支持非阻塞模式、注册到 Selector。

2.2 Buffer 缓冲区

Buffer 是一块内存容器，底层封装数组，4个核心标记：

  • capacity：缓冲区总容量，创建后固定不变
  • limit：读写上限，代表最多可以读到哪个位置
  • position：当前读写指针位置
  • mark：自定义标记，reset() 回到 mark 位置

高频方法：

  • flip()：写模式切换读模式 → limit=position，position=0
  • clear()：读模式切换写模式 → 重置标记位，不会清空底层数组数据
  • rewind()：position 置0，重新读取

💡flip() 和 clear() 的区别？
flip：写转读；clear：读转写。clear 只是重置指针，缓冲区里旧数据还在。

2.3 Selector 多路复用器

Selector 是 NIO 的灵魂：单线程可以监听成千上万个 Channel 的IO就绪事件
支持监听4种事件：

  • OP_ACCEPT：服务端，有客户端连接就绪
  • OP_CONNECT：客户端，和服务端连接成功
  • OP_READ：通道数据可读
  • OP_WRITE：通道缓冲区可写入

模型说明：NIO 属于同步非阻塞。只是等待就绪阶段不阻塞，当事件就绪后，拷贝数据到用户内存的操作依旧是同步的，需要自己线程处理。

💡Netty 为什么底层选择NIO，不使用AIO？
Linux 系统对AIO内核支持不完善，稳定性差；epoll（NIO多路复用）成熟稳定，所以Netty基于NIO封装。

2.4 BIO / NIO / AIO 对比表

IO模型 阻塞特性 同步/异步 线程模型 适用场景
BIO 阻塞 同步 一个连接一个线程 连接数少，简单传统业务
NIO 非阻塞 同步 Selector单线程轮询就绪事件，就绪后处理 高并发长连接（Netty、RPC框架）
AIO(NIO.2) 非阻塞 异步 内核IO完成后回调通知 Windows支持好，Linux落地少

三、File 与 NIO.2 Path & Files

java.io.File 不是流！它仅仅是文件/目录路径的抽象描述，不能直接读写文件内容。
常用方法：exists()、isFile()、isDirectory()、createNewFile()、mkdir()、delete()、listFiles()

Java7 NIO.2 新增 java.nio.file 包，Path、Files，API更简洁，推荐新项目优先使用：

💡File 和 Path 的区别？
File 是旧API，功能弱、很多方法异常不友好；Path 是NIO.2，配合Files工具类，支持符号链接、文件属性、更好的异常体系。

四、进阶考点：零拷贝

💡什么是零拷贝？有什么优势？Java哪里用到零拷贝？

传统IO流程：磁盘 → 内核缓冲区 → 用户缓冲区 → Socket缓冲区 → 网卡，发生多次内核态、用户态数据拷贝和上下文切换。
零拷贝（FileChannel.transferTo / transferFrom）由内核直接完成数据传输，减少用户态和内核态之间的数据拷贝，提升大文件传输性能。
Netty、RocketMQ、Kafka大量使用零拷贝优化传输性能。
